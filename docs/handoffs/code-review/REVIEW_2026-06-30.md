### 1. Magic number w regex action vs stała `_MAX_ACTION_LENGTH` (NAPRAWIONE)
`_ACTION_RE` miał zahardkodowany górny limit `{0,119}`, podczas gdy długość maksymalna
jest stałą `_MAX_ACTION_LENGTH = 120` (użytą też w `Field(max_length=...)`). Bump stałej
nie pociągnąłby za sobą regexa → cicha rozbieżność dwóch granic na ten sam atrybut.
Zmieniono na f-string `rf"...{{0,{_MAX_ACTION_LENGTH - 1}}}$"`. Wynikowy wzorzec
identyczny (`{0,119}`), zweryfikowane: 120 znaków akceptowane, 121 odrzucane, 7 testów zielone.

## Zweryfikowane, ale BEZ zastrzeżeń

- **Podział auth: create=bearer scope, list/approve=sesja ownera** — zamierzony consent
  gate (agent proponuje tokenem, owner zatwierdza zalogowany). Owner-scoping wszędzie
  przez `owner_user_id == current_user.id`. OK.
- **Brak efektów ubocznych przy walidacji błędnego payloadu** — `_summary_text` i
  `_payload_json` rzucają HTTPException 400 podczas konstrukcji obiektu, przed `db.add`;
  test potwierdza 0 wierszy w `AgentProposal` i `AgentAuditLog`. OK.
- **Redakcja sekretów w audycie** — `_audit_proposal` loguje tylko `action`/`proposal_id`/
  `proposal_action`/`token_id`, nie kopiuje payloadu; test sprawdza brak `not-copied-to-audit`. OK.
- **Round-trip payloadu** — zapis `json.dumps(sort_keys=True)`, odczyt `json.loads`
  z fallbackiem na `{}` przy złym JSON / nie-dict. Równość dict ignoruje kolejność kluczy. OK.
- **Idempotencja approve i guard statusu** — approved zwraca bez nowego auditu;
  rejected/non-pending → 409; cudza propozycja → 404 (nie 403, nie wycieka istnienia). OK.
- **Migracja schematu** — projekt używa `Base.metadata.create_all` (brak Alembica);
  nowa tabela `agent_proposals` tworzy się automatycznie, brak zmian kolumn w istniejących
  tabelach → `_migrate_schema()` nie wymaga rozszerzenia. `AgentProposal` dopięty do listy
  `touch_timestamps` (before_insert/update). OK.
- **Regex action zakotwiczony** `^...$` — Pydantic v2 stosuje pattern bez auto-anchoringu,
  ale wzorzec jest jawnie zakotwiczony. OK.
