## Naprawa zastosowana (prosta, bezpieczna)

### F1 — `interrupts.py`: brak guardu na pokonany **source** interruptu  ✅ NAPRAWIONE

`_apply_order_like` (handler Rozkaz/Klątwa/Oznaczenie) walidował `target` na
`models_alive == 0` ("not found or defeated"), ale **source** sprawdzał tylko na
`is None`. Asymetria względem `get_eligible_interrupts`, który filtruje
`models_alive == 0` (interrupts.py:134). `trigger_interrupt` **nie** pre-filtruje
source (dispatch-only) — więc gdy B4-orkiestracja (wątek H2, `WAITING(B4)`) wywoła
`trigger_interrupt` bez przejścia przez `get_eligible_interrupts`, pokonany oddział
(models_alive==0, wciąż w `state.blobs`) mógłby wydać Rozkaz/Klątwę i skonsumować
slot raz-na-rundę. Replay odtworzyłby to wiernie → deterministyczne, ale niezgodne
z regułami.

**Fix:** guard source mirror do targetu:
```python
if source is None or source.models_alive == 0:
    raise InvalidInterruptError(f"{slug}: source unit {source_id} not found or defeated")
```
Defense-in-depth, lustrzane do istniejącego filtra. Żaden istniejący test nie
ćwiczy pokonanego source przez tę ścieżkę → bez regresji (45 testów
order-abilities/interrupts + pełne 1593 zielone). Notatka dodana w
HANDOFF_faza-b-order-interrupts.md.

### F2 — `balance_simulate.py`: oba boty z **identycznym seedem** → bias mirror-matchu  (handoff)

`simulate_balance` (scripts/balance_simulate.py:253) buduje obu graczy z tym samym
seedem: `[make_player(kinds[0], seed), make_player(kinds[1], seed)]`. Dla
`random vs random` (domyślny matchup) na symetrycznej fixturze oba `random.Random(seed)`
generują **lustrzane** strumienie decyzji → systematyczny bias P0/P1 zamiast ~50/50.
Podważa to wiarygodność metryki balansu (cały cel narzędzia D2).

**Dlaczego nie auto-fix:** zmiana metodyki seedowania zmienia WSZYSTKIE liczby w
raportach balansu I łamie asercje w `test_balance_simulate.py` (przybite pod obecne
seedowanie). To decyzja metodologiczna, nie czysty bugfix. → **HANDOFF_balance-sim-seed-bias.md**.

### F3 — `state.py`/`effective_passives`: nadana pasywka omija walidację `b_mvp_exclusions`/`INCOMPLETE_ABILITIES`  (obserwacja)

`effective_passives(blob)` aplikuje override Rozkaz(X)/Klątwa(X) filtrowany tylko
przez `rozkaz_tak`, BEZ sprawdzenia `b_mvp_exclusions` / `INCOMPLETE_ABILITIES`,
które `build_initial_state` egzekwuje (UnsupportedAbilityError). Jeśli ruleset
oznaczy ability `rozkaz_tak:true` która jednocześnie jest na liście wykluczeń →
runtime wstrzyknie slug, którego agregatory cicho zignorują (brak modyfikatora) →
cichy no-op reguły (gracz zapłacił koszt/slot, zero efektu), zamiast jawnego błędu
jak w build-time. **Warunkowe** (zależy od konfiguracji rulesetu — dziś żadna
ability nie jest jednocześnie rozkaz_tak+excluded). Kandydat na walidację w
follow-upie order-interrupts (H1/H2). Odnotowane w HANDOFF_faza-b-order-interrupts.

### F4 — `combat.py`: `is_hero_unit` nie reaguje na override `effective_passives('bohater')`  (obserwacja, low-conf)

### F5/F6 — jakość heurystyk botów (obserwacje — wpływ na wiarygodność porównań balansu)

- **`greedy_player.py:144`** — `round(dist.expected_models_killed())` zaokrągla
  oczekiwane zabicia <0.5 do 0 → atak który prawdopodobnie zdjąłby ostatni model
  wroga z celu rejestruje `objective_delta=0`. GreedyPlayer niedoszacowuje ataków
  zdejmujących obrońcę z celu. Heurystyka, nie bug silnika; wpływa na metrykę D2.
- **`priority_v2_player.py:73`** — `_best_target` dla szarży (melee) skoruje cele
  modelem `expected_damage` który stosuje LoS/cover (model strzelania) → wybór celu

  dystansie → v1 i v2 rozjeżdżają się na wyborze szarży przez ranged-only heurystykę,
  skażając porównanie v1-vs-v2 (cel pliku v2).

Obie to jakość botów (nie błędy poprawności). Kandydaci na tuning w wątku graczy
heurystycznych (faza-d), jeśli metryka balansu ma być wiarygodna.
