### 1. Ciche odrzucenie jednostek z `AdaptResult` (UWAGA, nie naprawiam)

`roster_to_engine_roster` zwraca `AdaptResult` z polami `dropped_excluded`,
`inert_incomplete` oraz **`deferred_attached_heroes`**. `create_battle` bierze wyłącznie
`.units`, ignorując pozostałe. Skutek: roster zawierający **dołączonego bohatera**
(`parent_roster_unit_id is not None`, `roster_adapter.py:247-250`) utworzy bitwę bez tej
jednostki, bez żadnego sygnału do wywołującego. To znany dług MVP (heroes „DEFEROWANE w
slice 1"), więc **nie jest to regresja** — endpoint po prostu dziedziczy ograniczenie
adaptera. Nie naprawiam autonomicznie (zmiana kontraktu API / zakres B-engine).
Notatka dopięta w `HANDOFF_faza-b-engine-mvp.md`.

## Zweryfikowane, ale BEZ zastrzeżeń

- **Refaktor auth (`_authorized_owner_user_id`)** — wyodrębnienie wspólnej logiki
  bearer-vs-sesja z parametrem `agent_scope`; `_battle_reader` zachowuje identyczne
  zachowanie (401 przy braku auth, delegacja do `require_agent_scope`). Testy
  reader + nowy creator (401/403) zielone. OK.
- **`save_events(..., expected_latest_sequence=0)`** — nowa bitwa po `db.flush()` ma
  `id`, zero eventów; guard optymistyczny (commit `5fc1a47`) poprawnie oczekuje 0.
  `deployment_round` numeruje `seq` od 1 → sekwencje `1..N` ciągłe (test to sprawdza). OK.
- **`rng_seed` zapisany, nieużyty w `setup_phase`/`deployment_round`** — deployment jest
  **deterministyczny** (brak rzutów kości; tylko MoveExecuted/StatusAdded), więc seed nie
  wpływa na eventy tworzenia. Seed przechowany dla przyszłych rund (resume z persisted
  state). Brak błędu na tym etapie. OK — do obserwacji przy implementacji rund bojowych.
- **Owner-scoping i kolizje ID** — oba rostery adaptowane z `owner_player=0/1`; ID bloków
  używają `owner_player * _PLAYER_ID_STRIDE`, brak kolizji nawet gdy `p1_roster_id ==
  p2_roster_id`. `p1_user_id == p2_user_id == creator` — zamierzone (bitwa solo ownera,
  potwierdzone w teście). OK.
- **Atomowość** — walidacja rosterów (404) przed `db.add`; test potwierdza 0 wierszy
  `Battle` po odrzuceniu. `db.flush`/`save_events`/`db.commit` w jednej transakcji. OK.
- **Walidacja wejścia** — `p1/p2_roster_id ge=1`, `initiative_player` `ge=0 le=1`,
  `rng_seed` int default 0. OK.
